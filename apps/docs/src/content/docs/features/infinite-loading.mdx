Give the table a `dataSource` instead of `data`, and it asks `getRows({ start, end, sorting, filters, quickFilter, signal })` for the pages in view (`end` exclusive), showing skeleton rows until they arrive. Fast scrolling loads only where it stops, and pages that scroll away are aborted through `signal`. Sorting happens on the server: a new order reloads from the top. The source here is a pretend server in `data.ts` that answers after a short delay; this one sends the total, 100,000 rows.

Create the source once. A new source object starts again from an empty cache, so building one on every render would reload the table each time.

The rows can form a tree whose children load as rows expand, through the source's `hasChildren` and `getChildren`: see [children from the server](../tree-rows/#children-from-the-server) <Since since="1.4" />.

## Without a total

Leave `total` out and the table keeps one page of skeletons below the last row it has; a page with fewer rows than asked for marks the end. Until then, `aria-rowcount` is -1, which tells screen readers the size is unknown. This server has 2,350 rows.

## Failed pages

When `getRows()` rejects, the page's rows show as error skeletons, the table fires `argus-load-error` with `{ error, start, end }`, and the first visible row of the page gets a Retry button (Enter on any cell of the row retries too). Here the first page fails once. `refresh()` drops every page and loads the rows in view again.
