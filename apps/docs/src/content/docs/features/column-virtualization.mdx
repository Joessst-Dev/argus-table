Rows are always virtualized. With `virtualizeColumns` (`virtualize-columns`), columns are too: the scrolling columns in view render, plus two on each side, and pinned columns always render. Here 503 columns and 10,000 rows render a few hundred cells. Keyboard focus still reaches every column: End jumps to the last one, and the table scrolls it into view.

Turn it on for wide tables. Without it, every column renders in every row: 503 columns here would mean 12,000 cells, and every one of them is work when the table scrolls or its columns change.

Removing many cells at once is slow in Safari. Each cell's content goes to a slot of its own, and WebKit takes longer to empty a slot the more slots a table has, so the time grows with the square of the cells removed. Adding cells doesn't: the table adds them in an order WebKit handles in linear time. Turning column virtualization off (adding cells) and on again (removing them) for a table of 10,000 rows with 33 rows rendered, measured in Playwright's WebKit and Chromium:

| Columns | Cells rendered | Off: WebKit | Off: Chromium | On again: WebKit | On again: Chromium |
| ------- | -------------- | ----------- | ------------- | ---------------- | ------------------ |
| 50      | 1,700          | 0.4 s       | 47 ms         | 0.9 s            | 58 ms              |
| 100     | 3,400          | 0.5 s       | 90 ms         | 2.1 s            | 0.2 s              |
| 200     | 6,800          | 0.8 s       | 0.2 s         | 6.3 s            | 0.5 s              |
| 500     | 17,000         | 1.7 s       | 0.4 s         | 50 s             | 2.6 s              |

So turn it on once a table has more than about 30 columns, or fewer on tall screens, where more rows are in view: what counts is the number of cells. Below that, rendering every column costs less than tracking which are in view. The details are in [issue #168](https://github.com/Joessst-Dev/argus-table/issues/168).
